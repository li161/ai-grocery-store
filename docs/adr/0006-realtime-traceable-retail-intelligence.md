# ADR-0006：零售情报采用可追溯近实时信源流水线

## 状态
Accepted

## 背景
零售情报不是静态内容页。目标是持续发现零售 AI、Agentic Commerce、库存、导购、支付等公开信息，同时保证用户可以回到原始信源核对。

## 决策
- 使用公开 RSS/新闻源作为发现层。
- 每 5 分钟由 GitHub Actions 执行一次同步；GitHub 官方文档说明 scheduled workflow 最短可配置为 5 分钟，但高负载时可能延迟，因此产品文案使用“近实时雷达”，不宣称严格实时。 
- 同步结果同时写入 `src/data/retailNews.generated.js` 与 `public/retail-news.json`。
- 浏览器每 5 分钟重新拉取 JSON，并使用时间戳避免缓存。
- 页面保留标题、日期、原始来源和原文链接；自动抓取的新闻不再生成未经来源支持的“事实性摘要”。
- 本地精选案例可以保留人工整理的摘要，但必须附原始信源，并明确“已披露 / 已推进 / 待验证”等证据状态。
- 同一条情报最终必须能回到原始 URL；没有可追溯来源的数据不进入正式情报列表。

## 首页位置
零售情报作为店铺首页的第二层内容，紧接沉浸式 StoreHero 展示；侧边栏仍保留独立入口，方便直接进入完整情报时间线。

## 情报流水线
当前流水线进一步采用 AIHOT 类似的四段式结构：
1. **信源抓取**：RSS / Google News 聚合 + Amazon、Google、OpenAI、Anthropic、阿里、Walmart、京东等官方域名定向检索。
2. **大模型筛选**：可通过 GitHub Secret `OPENAI_API_KEY` 启用 LLM，对每条内容计算 `relevance / impact / novelty / evidence`，并过滤低相关噪音；未配置 Key 时自动使用本地规则评分，不阻断同步。
3. **事件聚簇与热度**：按标题语义词重合进行事件聚簇，并综合零售影响、时效、信源等级、事件覆盖量形成 `heatScore`，热点榜直接使用该分数。
4. **日报产出**：自动生成 `public/retail-daily.json`，页面展示当日重点事件和生成方法；日报不是另写一篇“新闻摘要”，而是对雷达结果的可追踪汇总。

LLM 的评分 Prompt 明确以“对零售经营的影响程度”为核心，而不是泛化的 AI 新闻热度。重点维度包括导购、转化、客单、库存、履约、人效、损耗、门店运营、支付和平台格局。

## 后续
当数据量扩大后，再增加：
1. 来源等级与可信度字段；
2. 事件去重与事件聚类；
3. 事件 → 案例 → 经营指标的证据链；
4. RSS 之外的官方公告、财报、监管披露等一手信源连接器。


## AIHOT-inspired event engine（增强版）
在原有“信源 → 筛选 → 热度 → 日报”基础上，增加事件级中间层。参考 AIHOT 的核心思想：资讯不是最终产品，**事件才是聚合与排序的基本单位**。当前实现为：

`信源抓取 → LLM 零售相关性/影响评分 → 候选事件召回 → LLM 判断 same/followup/new → 事件聚簇 → 独立信源计数 → 事件热度 → AI 零售日报`

- 候选召回：先用标题 token 相似度缩小候选集合，避免让 LLM 对全量内容两两比较。
- 事件判断：LLM 判断“同一事件 / 后续进展 / 新事件”，而不是简单依赖标题相似度。
- 事件热度：以独立来源数、官方信源、零售影响、相关性、证据质量和时间衰减计算，避免同一媒体重复转载直接堆高热度。
- 事件状态：`active / cooling`，为后续“持续追踪”预留状态机。
- 日报：以事件榜为输入生成，而不是直接从新闻列表拼接。
- 降级：没有 `OPENAI_API_KEY` 时仍使用本地规则和标题相似度，不影响基本同步；配置 Key 后启用 LLM 筛选、事件判断和日报编辑。

### 与经营结果的连接
每个资讯条目保存 `eventId / eventTitle / eventHeatScore / eventSourceCount / eventWatch`，后续可以将一个事件直接关联到“经营结果”案例，从而形成“情报发现 → 事件演化 → 案例 → 经营指标验证”的闭环。
